## 1. The exact Step 7I boundary (R-1)

### 1.1 Step 7I implements

1. **The governed report-lifecycle database operations** — the reviewed, constrained `SECURITY DEFINER` mutation RPCs of §5, enforcing every transition guard the Step 7E migration's closing declaration deliberately deferred to Step 7I: exactly-nine completeness, approval freezing, write-once `submitted_at`/`submitted_by`, compare-and-set transitions via `lock_version`, no-report-for-an-absent-student, mid-cycle-absence progression blocking, new-version-on-every-accepted-change, and previous-submitted-stays-canonical.
2. **The three read models** — the canonical latest-submitted read (A-030's narrowed path, all three roles), the trainer-only working-state read, and **the management pre-submission final-review read (A-038)**. Each is required by the CAS contract itself: a caller cannot supply expected `status`/`lock_version`/version-id values it cannot read.
3. **Audit appends for the report lifecycle** — emission of `report.created`, `report_version.created` and `report.state_changed` through `public.audit_append_event`, in the same transaction as each business mutation. **No audit-registry extension is required or permitted** — every 7I event uses an action already in the ratified 16-action registry, so neither `audit_append_event` nor `audit_verify_chain` is replaced.
4. **The A-040 schema additions, exactly** — the `trainer_approved` enum label (added `AFTER 'needs_edit'`, in its **own** migration file); two correction-vocabulary enums; the correction-request table (with its `centre_id`, composite FKs, RLS enablement and explicit revokes); three `report_versions` columns; **four constraint replacements and one column-default drop**. **Two migration files** (U-7I-18).
5. **Three new functions beyond the RPCs** — the parent-reach authorization helper, the content serializer, and **the wording serializer** (§4.6).
6. **The server-action proof** — exactly one reviewed server action wired through the request-scoped authenticated client, demonstrating the Phase 0 exit condition (§9).

## 2. Status vocabulary (R-2)

The **eight** persisted `public.report_status` enum labels — the seven byte-exact from the Step 7E migration, plus the one label authorized by A-040:

| # | Stored label | Meaning | Visibility |
|---|---|---|---|
| 1 | `incomplete` | Required observation information missing (all nine dimensions — A-017); work preserved | Trainer only |
| 2 | `observation_saved` | Structured B.E.S.T record exists — all nine ratings present | Trainer only |
| 3 | `drafting` | Validated data undergoing AI generation (synchronous — ADR-5) | Trainer only |
| 4 | `draft_ready` | Draft ready for trainer Review & Approve | Trainer only |
| 5 | `needs_edit` | Trainer revision required — entered by a management assessment-level return, or by reopening a submitted report | Trainer only (§13's "authorised TA" is inoperative — A-014) |
| 6 | **`trainer_approved`** | **The trainer approved a specific version; management has been notified; the report is awaiting or undergoing management final review** | Trainer and management; **never a parent** |
| 7 | `approved` | **Management** approved the exact final version | **Transient-in-transaction only (R-8)** — never committed |
| 8 | `submitted` | Published; the canonical version is readable by all three roles | Parent and management read the canonical submitted version via the read RPC |

**Label position is ratified (Step 7I1D-R2).** The label is added **`AFTER 'needs_edit'`**, so the physical `pg_enum` sort order equals the workflow order of the table above and equals A-036, `CLAUDE.md` §6 and this document. A bare `ADD VALUE` would append it eighth and silently disagree with all four. Nothing in the MVP orders or ranges by `report_status` today — the ordering is pinned **before** anything depends on it. Proven by T7I-73.

**`trainer_approved` is the management-review state, and no ninth label is added.** An additional explicit "in management review" status was considered and **rejected**: it would encode UI presence rather than a governed fact, `trainer_approved` already carries every fact the lifecycle needs (a trainer approval exists, publication has not happened, management is the only actor who can move it), and A-036 forbids adding one for UI convenience. **This is a ratified decision, recorded here, not an omission.**

**`Evidence Pending` is a blocking flag concept, not a persisted status.** Step 7I creates no evidence representation of any kind; the only evidence-shaped input to the approve gate is the version-scoped checklist attestation `evidence_confirmed` (§3.4). A-001/A-003/A-004 apply in full whenever evidence is implemented.

## 3. Transition graph and matrix (R-3 … R-9)

### 3.1 Ratified rulings that shape the graph

- **R-4 — Lazy, trainer-actor report creation.** The `reports` aggregate is created by the assigned trainer's explicit lifecycle action, never by roster initialization. This satisfies "no report exists for an absent student" structurally, gives every `report.created` event a real authenticated trainer actor, and matches §13's `[*] → Incomplete` entry. Creation requires an existing `observations` row for the same (session, student) — `p_observation_id` is a required argument even though the column is nullable in DDL; the composite FK `reports_observation_fk` proves same-session-same-student.
- **R-5 — Create-per-change (ratified at 7I1B-R0, resolving B-7I-2).** **Every accepted content change creates a new immutable `report_versions` row.** There is no in-place mutation of version content at any point in the lifecycle. Versions are created by exactly four operations: the first draft store (T3), an accepted trainer save (T5/T6), an accepted management wording edit (T9), and the reopen-for-correction clone (T12). `revision_number` is a dense per-report ordinal assigned at version creation. **This restores exact agreement with the ratified Step 7H baseline §8**, whose originator column already named the save-edit RPC as an originator of `report_version.created` — the superseded in-place model was the party out of step, and no 7H supersession is required.
  - **Rating-snapshot sourcing follows the actor's authority.** A version created by a **trainer** operation (T3, T5, T6, T12) copies the **nine current `observation_ratings`**, so a trainer's rating correction propagates into the report. A version created by the **management wording edit** (T9) copies the **nine snapshots verbatim from its source version**, so management can never introduce, remove or alter a rating.
  - **Consequence, recorded:** version count now grows with edit activity rather than being bounded at one per correction cycle. This is the ratified cost of immutability and of `ai_jobs.result_version_id` stability; `report_versions_report_revision_key` and the aggregate row lock keep allocation correct at any volume.
- **R-6 — `trainerEdits` commits only on a successful save (ratified at 7I1B-R0, resolving B-7I-3).** Opening, closing or cancelling the report editor is **non-mutating**: it writes no row, changes no status, creates no version and emits no audit event. **The `report_begin_edit` RPC is removed entirely** — navigation is not a persisted state change, which also settles the 7H §1.4 E13 tension and A-029's data-minimization rule. A trainer save from `draft_ready` is the **self-transition T5**: it creates a new version and leaves the persisted status at `draft_ready`. A trainer save from `needs_edit` is **T6**: it creates a new version and advances to `draft_ready`. There is therefore no state in which a trainer who opened and abandoned an editor is trapped, and no abandon-edit arc is needed.
- **R-7 — Trainer approval is legal from `draft_ready` and from `needs_edit`** (both §13 arcs preserved), always and only through `report_trainer_approve`. **It publishes nothing.**
  - **R-7a — the target version must carry no trainer approval of its own (ratified at Step 7I1D-R2).** `report_trainer_approve` rejects, with a **named authored error**, any `p_expected_version_id` that already holds a `(version, 'trainer')` approval row. Without this precondition the arc's only failure mode would be a raw primary-key violation on a state §3.2 declares legal — an unauthored error in a legal state, which §3.2's own "0 rows matched ⇒ authored error" contract forbids. **Proven by T7I-75** (added at Step 7I1F-R3; the gate was previously stated but tested nowhere).
  - **Consequence, stated because it is not obvious: T8 is unreachable immediately after a management return.** T10 creates no version and moves no pointer, so the candidate is still the frozen version the trainer already approved. **T8's reachable origin is the T12 reopen clone**, which carries no approval. After a return the trainer must first produce a **new immutable correction version** through T6 — see R-7b.
  - **R-7b — reapproval after a return requires a new immutable version, and a content-identical one is permitted only as an explicit reaffirmation (operator ruling, Step 7I1D-R2).** Where the trainer inspects the flagged rating, observation or derived fact and concludes it is already correct, T6 may carry byte-identical panel content — but **only** when the caller supplies `p_reaffirm_correction_request_id` naming the report's open correction request. A **silent** byte-identical save is rejected with a named authored error, so "the trainer checked and stood by the assessment" is never recorded identically to "the trainer did nothing". The reaffirmation is durably linked through the correction request's own `resolving_version_id` (set when the corrected version is approved) and is named in the `report_version.created` payload. **No schema column is added for it** — the linkage already exists. Proven by T7I-71.
- **R-8 — `approved` is transient-in-transaction.** The only governed operation performing the `approve` transition is the management Approve & Submit RPC, which always continues to `submitted` in the same transaction. **No RPC commits with `status = 'approved'`**, so no committed `approved`-only residue can exist. The enum value remains — it is the ratified intermediate state, asserted inside the transaction and named in the two audit events. §13's "final submission may remain" resting state is now occupied by **`trainer_approved`**, which is a *committed* resting state; `approved` stays transient.
- **R-9a — Active-enrolment guard.** A-028 requires a report to exist "only where a **valid module enrolment** exists." `reports_enrolment_fk` proves only module-and-student agreement — it does **not** read `is_active`, and withdrawn enrolment rows persist. The structural constraint delivers the "never enrolled" half; the "valid/active" half is an explicit runtime guard:
  - `report_create` (T0) **resolves** `enrolment_id` itself from `(class_module_id, student_id) WHERE is_active` — the derivation must filter on `is_active`, because only the active row is unique (`enrolments_one_active_per_module_student_idx`). The enrolment id is **not** an RPC argument.
  - Every transition marked **[fwd]** re-checks `enrolments.is_active`. A-028 is silent on mid-cycle withdrawal; 7I ratifies the conservative reading — withdrawal blocks forward progress exactly as absence does, retains existing work, and unpublishes nothing (U-7I-8).
- **R-9 — Attendance and future-session guards.** Every transition marked **[fwd]** requires: (a) an `attendance` row for (session, student) with `status = 'present'` — **a missing row fails closed**; and (b) **the scheduled session start has been reached.**
  - **The future-session predicate is ratified (resolving B-7I-1): a report lifecycle action is locked while `now() < ((class_sessions.session_date + COALESCE(class_sessions.starts_at, TIME '00:00')) AT TIME ZONE 'Asia/Singapore')`.** The zone is a **pinned literal**, never the caller's `TimeZone` GUC, and **no per-centre timezone column, timezone UI or multi-centre timezone administration is added** — A-015's one-centre boundary stands.
  - **`starts_at` is nullable, and the fallback is ratified, not inferred.** Where a session records no scheduled start time there is no scheduled start to reach, and the **only total reading** of "unlock at the scheduled session start" against this schema is the **beginning of the session date in `Asia/Singapore`**. That reduces exactly to the previously drafted date-granular rule, so the two readings agree wherever `starts_at` is NULL and differ only where a real start time exists — which is precisely where the operator ruling applies. Recorded as an explicit adjudication (U-7I-13).
  - **The guard applies to trainer-side forward transitions only.** Spec §15 locks "assessment and drafting"; management's operations are structurally downstream of a trainer approval that already required the guard, so T9, T10 and T11 do not re-check it. `submitted → needs_edit` (T12, correction entry) is **not** forward progress and re-checks neither guard; the forward transitions of the correction cycle re-check both, which is the physical form of "mid-cycle absence retains existing work but blocks progression."

**The complete legal (from, to) set is these fourteen pairs and no others** (T11 contributes two): `∅→incomplete`, `incomplete→observation_saved`, `observation_saved→drafting`, `drafting→draft_ready`, `drafting→observation_saved`, `draft_ready→draft_ready`, `needs_edit→draft_ready`, `draft_ready→trainer_approved`, `needs_edit→trainer_approved`, `trainer_approved→trainer_approved`, `trainer_approved→needs_edit`, `trainer_approved→approved`, `approved→submitted`, `submitted→needs_edit`.

**Explicitly illegal, and structurally unreachable:**

- any committed `approved` state, and any path to `approved` outside T11's transaction (R-8);
- any direct path from `draft_ready`, `needs_edit` or `trainer_approved` to `submitted` — publication is reachable only through T11;
- any **trainer**-initiated transition out of `trainer_approved`: the trainer cannot un-approve, withdraw, or edit past their own approval. A change after trainer approval is reachable only through management's wording edit (T9) or management's return (T10);
- any **management**-initiated transition other than T9, T10 and T11 — management cannot create a report, save a draft, run the assessment lifecycle, or reopen a submitted report;
- any **parent**- or **AI**-initiated transition of any kind (A-021; "AI never publishes directly");
- any exit from `submitted` other than T12 (A-028: "the only exit");
- every skip arc (`incomplete → drafting`, `observation_saved → draft_ready`, `needs_edit → submitted`, `draft_ready → submitted`, …);
- any un-approve, revoke, or approval-deletion arc for either role.

A partial save of observation data in `incomplete` is not a report transition at all — it mutates `observations`/`observation_ratings` (assessment-checkpoint scope) and leaves the aggregate untouched.

### 3.3 Checklist updates (not a transition)

`report_update_checklist` mutates the **working version's** three booleans without changing status and **without bumping `lock_version`**; instead it **validates** the caller's expected `lock_version` and expected current-version id, and requires `status ∈ {'draft_ready','needs_edit'}`. Not bumping `lock_version` is deliberate — a checklist tick is not a content change and must not invalidate a concurrent editor's expectations.

**The status test alone is insufficient, and this was a real hole (corrected at Step 7I1D-R2). Two further gates are ratified:**

> **Gate A — the target version must hold no approval row.** `report_update_checklist` rejects, with a named authored error, any `p_expected_version_id` for which a `report_version_approvals` row exists.
> **Gate B — the target version must be trainer-authored.** It rejects, with a distinct named authored error, any version whose `authored_by_role` is `management` — such a version has **no checklist row at all** by §3.3's own rule, and the operation must fail loudly rather than create one.

**Why both are load-bearing.** The two-stage workflow creates a state the superseded single-stage design never had: **`needs_edit` whose `current_cycle_version_id` names a version that is not an open trainer working version.** T10 (management return) produces it in two shapes:

- **after a return with no prior wording edit** — the candidate is the **frozen, trainer-approved** version. The status gate (`needs_edit` ✓), the `lock_version` gate and the current-version gate **all pass**, so without Gate A the RPC would overwrite the checklist evidence attached to a frozen approved version — violating §4's own freeze rule ("no RPC writes any `report_version_checklist_progress` row for it"), A-028, and `CLAUDE.md` §6's "a frozen version's checklist and approval evidence are immutable and must never be cleared", and falsifying T7I-17. U-7I-9 deliberately adds no guard trigger, so **contract is the only enforcement and the contract must therefore state it**;
- **after a return that followed a wording edit** — the candidate is a **management-authored** version carrying no checklist row, where the operation's behaviour was simply undefined. Gate B defines it: reject.

**Neither gate traps the trainer.** In both shapes the correct next action is a governed save (T6), which creates a new trainer-authored version with a fresh all-false checklist row that the trainer may then tick normally. Proven by T7I-64.

**The validation must be performed under the aggregate row lock.** A plain `SELECT … WHERE lock_version = $v` reads a statement snapshot and serializes against nothing, so this interleaving is admissible: (1) the checklist RPC reads matching expectations; (2) a save commits, creating a new version and bumping `lock_version`; (3) the checklist RPC, still holding its stale read, writes an all-true checklist. Under R-5 the damage is narrower than under the superseded in-place model — the checklist would land on a **superseded** version rather than on the newly-written text — but it is still a false attestation on a row the approve gate could read if the expectations were replayed. **Ratified:** `report_update_checklist` acquires `SELECT … FROM public.reports WHERE id = p_report_id FOR UPDATE` as its first statement, validates status, `lock_version` **and** current-version id under that lock, and only then writes. **Locking is the fix; bumping is not.** (The converse race, two concurrent checklist writes, is benign: the signature is a full-state write of all three booleans, so last-writer-wins can only produce a false negative — approval blocked — never a false positive.)

**The checklist is a trainer instrument, and only a trainer instrument.** It attests that *this trainer* reviewed *this exact text*. Consequences, ratified:

- every **trainer**-created version (T3, T5, T6, T12) gets a fresh all-false checklist row;
- the **management wording-edit version (T9) gets no checklist row at all** — management is never asked to satisfy, and can never satisfy, the trainer's attestation, and an all-false row on a version that can never be trainer-approved would be misleading. Every read model must therefore tolerate a version with no checklist row;
- **management's Approve & Submit does not read the final version's checklist** (there may be none). It copies the three checklist **boolean values** from the **trainer-approved source version's trainer approval row** into the management approval row, so the all-true CHECK is satisfied by a true fact: the trainer's gate *was* satisfied for the lineage being published. **This copies evidence values, not an approval** — no trainer approval row is created, duplicated or implied for the management-edited version (R-12a item 5).

**`CLAUDE.md` §6's invariant is preserved literally, and this is the sharpest objection to the two-stage design, so it is answered explicitly.** The rule is that the checklist "attests to **this exact text**." Under this design the checklist row is attached, permanently and immutably, to the version whose text the trainer actually reviewed — it is never carried forward, never reset onto later text, and never re-pointed. When management edits wording, the published text differs from the text the trainer attested to; that is exactly what the operator ratified in A-034, and it is covered by its **own** provenance: a distinct immutable version, management authorship, explicit lineage to the trainer-approved source, its own content hash, its own audit event, and a management approval row naming the exact version published. **No attestation is ever transferred to content its author did not see.**

No audit event is appended for a checklist write (7H registry E10 excludes per-toggle audit; the approval event proves the gate for the exact version).

### 3.4 The evidence condition of the approve gate (Phase 1 form)

Spec §13 guards approve on "evidence = uploaded OR not_required." That condition is unimplementable in Phase 1: no evidence table exists (A-032), the uploader is UNRESOLVED (A-014), and A-028 explicitly defers "the representation of any evidence gate." **The Phase 1 trainer-approval gate's evidence condition is the version-scoped checklist attestation `evidence_confirmed = true`** — the trainer's accountable attestation, server-verified for the exact version — and nothing more. When evidence is implemented (Phase 2, conditional), its gate arrives with its own ratified representation and is **additive**, never a replacement that weakens it (U-7I-2).

## 4. Report and version model (R-10 … R-13)

Built on the five existing Step 7E report tables plus the **one new correction-request table** and the **three new `report_versions` columns** authorized by A-040. Three rulings govern this section: **R-10** — the mutability boundary; **R-11** — version numbering, lineage and pointer movement; **R-12** — snapshot, checklist, approval-cardinality and supersession behaviour. **R-13** is the §4.6 hash contract.

- **Authoritative mutable rows:** (a) the `reports` aggregate — the single owner of `status`, `lock_version`, `current_cycle_version_id`, `latest_submitted_version_id`; (b) the **current-cycle trainer-created version's** `report_version_checklist_progress` row, until that version is trainer-approved; (c) the correction-request row's resolution fields. **Under R-5 no `report_versions` content is ever mutable** — a version's content columns are written exactly once, at INSERT.
- **The freeze predicate is COLUMN-level, not row-level.** A row-level rule ("no RPC writes a version that has an approval row") is **false as stated and would break Approve & Submit**: §6.4 inserts the management approval row and then writes `submitted_at`/`submitted_by_*` on that same version, in the same transaction. The ratified rule is:
  > Once **any** approval row exists for a version, **no RPC writes** `todays_strength`, `next_focus`, `practice_suggestion`, `session_takeaway`, `content_hash`, `content_hash_version`, `revision_number`, `derived_from_version_id`, `trainer_approved_source_version_id` or `authored_by_*` on that version, and **no RPC writes any** `report_version_ratings` **or** `report_version_checklist_progress` **row for it**. The sole permitted post-approval write is T11's one-time population of `submitted_at`, `submitted_by_membership_id` and `submitted_by_role`, and only where all three are currently NULL.

  Under R-5 this rule is *belt and braces*: no RPC writes version content after INSERT under any circumstance, approved or not. Enforcement is by contract plus privilege — the only write paths are the ratified RPCs, and no client role holds DML on any report table. **Guard triggers are deliberately not added** (U-7I-9), justified by zero client DML, Step 7E's explicit assignment of approval-freezing to "the Step 7I transition functions", and the T11 carve-out that a naive trigger would break.
- **Version authorship is always written, and its role is now meaningful.** `authored_by_membership_id` / `authored_by_role` are stamped at every INSERT: `trainer` for T3, T5, T6 and T12; **`management` for T9**. A-040 widens the role pin from `trainer` to trainer-or-management precisely so a management wording edit is attributable; the composite FK still proves the membership genuinely holds that role. A Step 7I assertion proves no `report_versions` row carries a NULL `authored_by_*` pair.
- **Version numbering and ordering:** `revision_number` starts at 1 per report and increments by 1 at each version creation; `report_versions_report_revision_key` enforces uniqueness; ordering authority within a report is `revision_number`. **Allocation is serialized by the aggregate row lock:** every version-creating RPC takes `SELECT … FOR UPDATE` on the `reports` row **before** computing the next `revision_number`, so a concurrent pair fails with an authored error rather than a raw unique violation.
- **Two distinct lineage columns, with distinct meanings — do not conflate them.**
  - `derived_from_version_id` (existing) — the **immediate predecessor**. Set on every version except the first (T5, T6, T9, T12 all set it). Same-report by composite FK; not-self by CHECK; non-unique, so a branch is representable.
  - `trainer_approved_source_version_id` (**new**, A-040) — the **root trainer-approved version** of the current publication lineage. It is **NULL on any version that is itself trainer-approved or that precedes trainer approval**, and is set **only** by T9 to the resolved trainer-approved source. It is *not* the immediate predecessor: a second management wording edit points at the same trainer-approved root as the first, not at the intermediate management version.
  - **Resolution rule, used by every management gate:** the trainer-approved source of version `V` is `V` itself when `V` carries a trainer approval row, otherwise `V.trainer_approved_source_version_id`. If neither resolves, the version has no trainer approval behind it and **management may not submit it**.
- **`updated_at` maintenance:** Step 7E creates no triggers, so `updated_at` is not self-maintaining. Every RPC that writes one of those rows sets `updated_at = now()` in the same statement. A frozen version's `updated_at` is never touched after approval except by T11's one-time submission write.
- **Current-version selection:** `current_cycle_version_id` = the working or final-review candidate version (moves at T3, T5, T6, T9 and T12); `latest_submitted_version_id` = the canonical readable version (moves **only** at T11). During a correction cycle the two pointers deliberately diverge; the previously submitted version, its snapshots and its approval rows remain byte-stable while new work proceeds — readers never see a gap, a partially-corrected report, or draft content (A-028).
- **Rating snapshot behaviour (R-5).** T3, T5, T6 copy **all nine** current `observation_ratings`; T12 copies the frozen source's nine; **T9 copies its source version's nine verbatim**. Every approval gate independently asserts exactly nine rows exist for the version being approved, and **management's submission gate additionally asserts nine-way parity against the trainer-approved source** (§6.4). A version is self-contained — a reader never reconstructs an approved report from mutable working data.
- **Approval-row cardinality (R-12, A-037).** The primary key becomes **(version id, approver role)**, so **at most one trainer approval and at most one management approval may exist per version, ever**. Approval presence — not any column on the version — remains the sole authority for "this version is approved, and by whom." The role is pinned by CHECK to trainer-or-management and by composite FK to a membership genuinely holding that role, so an approval by the wrong role stays unrepresentable.

  > **"At most one of each" is a ceiling, not a requirement. No version ever requires both approvals**, and whenever management edits wording the published version carries only a management approval. See R-12a immediately below.

- **Superseded versions:** a superseded version remains permanently frozen and permanently retained (append-only history; its approval rows and snapshots prove what was reviewed, approved and published, and when).
- **Edit after trainer approval:** only management's wording edit (T9), which creates a new version and never touches the frozen one. **Edit after submission:** only T12. **Reapproval:** any version created after a trainer approval — whether by a trainer correction or a management wording edit — re-enters the appropriate gate. A trainer correction requires a **fresh trainer approval** on the corrected version; a management wording edit requires **no trainer reapproval** (A-034) but does require management's own approval on the exact version submitted.

### 4.4 Approval provenance — the exact model (R-12a)

**Each approval belongs to the exact version its actor reviewed, and to no other version. Nothing is copied, inherited or fabricated across versions.**

1. **A trainer approval belongs to the exact trainer-reviewed source version.** `report_trainer_approve` writes it against `p_expected_version_id` after verifying that version's checklist, its nine snapshots and its content hash. It is never re-pointed, re-dated, duplicated onto a descendant, or transferred.
2. **A management wording edit creates a new immutable descendant version.** It never writes to the trainer-approved version, and it never creates, copies or synthesises a trainer approval row for the descendant. **A management-edited version carries no trainer approval row at all** — and that absence is correct, because no trainer reviewed that exact text.
3. **The descendant retains `trainer_approved_source_version_id`**, pointing at the **root** trainer-approved version of its publication lineage (not its immediate predecessor — that is `derived_from_version_id`). A second wording edit points at the same root, so the lineage never drifts through an intermediate management version.
4. **A management approval belongs to the exact final version submitted** — the version the canonical pointer will name. It is written by `report_management_approve_and_submit` against that version and no other.
5. **The three checklist columns on a management approval row are evidence, not an approval.** They record that the **trainer's** gate was satisfied for the lineage source, copied from that source's trainer approval row so the all-true CHECK is satisfied by a true fact. **They are not a trainer approval, they do not create one, and they never make the management row count as one.** The trainer approval row itself stays exactly where the trainer put it.
6. **Submission verifies valid lineage to a *current* trainer-approved source.** The CAS in §6.4 step 3 proves the version being submitted is the report's current candidate; step 4 then resolves that version's trainer-approved source and requires it to carry a trainer approval row. A stale, superseded or absent source cannot pass.
7. **All nine ratings must be identical to that source** (§6.4 step 5), re-verified at submission independently of how the version was produced.
8. **A substantive assessment change is never reachable through management.** Any change to a rating, an observation, or a fact derived from one requires a **return to the trainer**, the trainer's correction through the governed workflow, and a **fresh trainer approval** on the corrected version — which then begins a new publication lineage with its own root.

**The two published shapes, stated explicitly so no reader infers a requirement that does not exist:**

| Case | Trainer-approved source version | Submitted version | Approval rows that exist |
|---|---|---|---|
| **Management approves unchanged** | version *V* | the same version *V* | *V* carries **both** a trainer row and a management row — because one version was both reviewed and published |
| **Management edits wording** | version *V* | descendant *V′* (`trainer_approved_source_version_id` = *V*) | *V* carries **only** a trainer row; *V′* carries **only** a management row. **Neither version carries both, and this is the expected outcome, not a defect** |

**One new table**, `report_correction_requests`, carrying exactly the ratified minimum representation and nothing more:

- **At most one `open` request per report**, enforced by a **partial unique index restricted to `status = 'open'`** — the Step 7E pattern, so resolved history never blocks a later request.
- **Exactly two status values.** A `withdrawn` value was considered and **rejected**: no ratified operation withdraws a request, and A-026 forbids inventing an enum value for an unratified workflow.
- **Resolution is a side effect of trainer reapproval, not a separate operation.** `report_trainer_approve` resolves the report's open request, if any, in the same transaction — setting `status='resolved'`, the resolving trainer, the time, and the newly trainer-approved version. No standalone "resolve" RPC exists, so a request cannot be closed without the corrective work actually being approved.

This is deliberate: an audit row is permanent and unredactable, a human-written reason may contain identifying detail, and the correction-request row is an ordinary application row a future PDPA mechanism can reach.
- **Ratified reason bound: 2,000 characters** — comfortably sufficient for a specific, actionable correction note and far short of a free-form log. **Confirmed by the operator at Step 7I1D-R2 and no longer a reviewable default: U-27 is resolved.** The table is provably empty, so the bound stays trivially adjustable, but it is now a decision rather than a placeholder.
- **Client access and RLS posture:** none, and **stated in full at Step 7I1D-R2** — the earlier "zero client grants and zero policies" was incomplete. The table receives:
  - **`ALTER TABLE public.report_correction_requests ENABLE ROW LEVEL SECURITY`** with **zero policies**;
  - an explicit **`REVOKE ALL ON TABLE public.report_correction_requests FROM PUBLIC, anon, authenticated, service_role`**;
  - **no grant of any kind.**

  **Zero grants is not the same as RLS enabled**, and the distinction is not academic here: the committed fixture verifier's label **A32** counts **every** relation in `public` and fails if any has `NOT relrowsecurity`. A new table shipped without RLS enabled would fail A32 in a way indistinguishable from a real posture regression. A-030's rule is "RLS **enabled** on all tables with zero policies", and privilege and policy are two separate layers. Proven by T7I-3 and by the reconciled A32.

### 4.6 Content hash and wording hash — columns, algorithms, serialization (R-13; U-7I-1)

**Fact record:** Specification v3 §20 lists `content_hash` on `report_versions`; the Step 7E migration deliberately omitted it with a written comment forecasting "it therefore arrives with Step 7H"; Step 7H's ratified baseline scoped Step 7H to audit objects only and did not include the column. The column therefore **does not exist today**, while the ratified 7H event contract and v3 §23 approval provenance **require its value at Step 7I**.

**Ruling:** the column arrives with **Step 7I** — the checkpoint that gives it meaning. The 7E comment's "arrives with Step 7H" was a forecast, not a ratified assignment, and is corrected here **in writing, not silently**; the migration attaches a `COMMENT ON COLUMN` recording the correction so it is visible in the schema itself (the 7E migration file is never edited).

**Columns (two, both added by the Step 7I migration; A-040):**

- `report_versions.content_hash text NOT NULL`, constraint **`report_versions_content_hash_chk CHECK (content_hash ~ '^[0-9a-f]{64}$')`** — the exact shape and constraint style of `audit_events.prev_hash`/`entry_hash`. NOT NULL is safe without a DEFAULT because the table is provably empty (the fixture loader aborts unless all five report tables are at zero rows; Step 7F Option B ratifies zero `report_versions`).
- `report_versions.content_hash_version smallint NOT NULL DEFAULT 1`, constraint **`report_versions_content_hash_version_chk CHECK (content_hash_version = 1)`** — the exact mirror of `audit_events.canonical_version`. Without it the algorithm that produced a stored hash is unrecoverable from the row. A future envelope increments this value and adds a **parallel** serializer; committed rows are never re-serialized.

**Two serializers, both named, argument-pure, and neither reachable by any client.**

1. **`public.report_content_hash_v1(p_todays_strength text, p_next_focus text, p_practice_suggestion text, p_session_takeaway text, p_ratings public.competency_rating[]) RETURNS text`** — the **full content identity**, covering the four panels **and** the nine ratings. This is the value stored in `content_hash`, carried in audit payloads, and used for trainer approval provenance.
2. **`public.report_wording_hash_v1(p_todays_strength text, p_next_focus text, p_practice_suggestion text, p_session_takeaway text) RETURNS text`** — the **parent-facing wording identity**, covering the four panels **only**. Domain-separated as `BESTCOACH-REPORT-WORDING-V1`. **It is never stored**; it is computed on demand by the management read and re-verified by the management mutations, so it cannot drift from the content it describes.

**Both are `LANGUAGE plpgsql`** — stated explicitly at Step 7I1D-R2, because the language was previously unspecified and two ratified claims depend on it. `plpgsql` is chosen because the content serializer must **raise** on a rating array that is not exactly nine non-NULL elements, which a `LANGUAGE sql` body cannot do cleanly. Neither serializer references `'trainer_approved'`, so the A-040 enum-sequencing constraint does not reach them; both ship in the second migration file regardless.

Both are `IMMUTABLE`, **not `STRICT`** (the four panel columns are NULLABLE and a NULL panel is a legal, meaningful value serialized as the `N` tag), `PARALLEL SAFE`, `SECURITY INVOKER`, `SET search_path = ''`, owner `postgres`, with explicit `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role, authenticator` and **no `GRANT`** — no client EXECUTE of any kind. Both **read no table**: every hashed value arrives as a parameter, which is what makes `IMMUTABLE` factually correct rather than merely asserted, and what lets them be independently recomputed and tested.

> **How argument-purity is actually proven (corrected at Step 7I1D-R2).** An earlier draft of T7I-45 proposed proving it from `pg_depend`. **That proof is vacuous for a `plpgsql` function:** PostgreSQL stores a PL/pgSQL body as opaque text and records **no** `pg_depend` entry for any relation referenced inside it, so the assertion would pass by construction whatever the body contained. Argument-purity is therefore proven by a **static scan of `pg_proc.prosrc`** for any `FROM`, `JOIN` or schema-qualified relation reference, plus a runtime determinism proof across sessions. The `pg_depend` check is retained only as a **negative cross-check on the function's argument and return types**, and is explicitly not claimed to prove purity.

**R-26 — why a second hash exists, and why this is not redundancy.** The content-hash preimage covers the nine ratings, and a rating is one of only four enum values. **A reader holding the four panels and the content hash recovers the exact per-dimension rating grid by exhausting 4⁹ = 262,144 SHA-256 candidates** — trivial work on a phone. Under the two-stage workflow **management holds the four panels by design and is the actor who must supply a "this is the exact text I approved" proof at submission**, so returning the content hash to management would reconstruct precisely the artefact `CLAUDE.md` §6 names as a caught leak to be fixed, and that A-021 forbids as raw private assessment data. Publishing the envelope grammar in this repository is not a mitigation — obscurity is not a control anywhere else in this project and is not one here.

**Ratified: the content hash is trainer-only. Management's stale-render proof uses the wording hash, which leaks nothing because it checksums data the reader already holds in full.** Alternatives compared and rejected: **(a)** drop the caller-supplied proof for the management stage — rejected, it removes the exact stale-render guard the proof exists for, at the one stage where two humans and a wording edit sit between review and publication; **(b)** return the content hash to management under an explicit "raw private assessment data" carve-out — rejected, it recreates the caught leak and would need its own amendment; **(c)** redesign the content-hash preimage so panels-plus-hash is not brute-forceable — rejected, it changes trainer provenance and the ratified E2/E3 audit payload contract to solve a reader-side problem, and any such design still leaks to whoever holds both values.

**Algorithm (both):** SHA-256 via core `pg_catalog.sha256(bytea)` — the project's already-ratified integrity primitive; no extension.

**Preimage, `content_hash_version` = 1:** the ratified length-prefixed envelope grammar of the 7H baseline §4.2, domain-separated on its own line, LF-terminated, followed by fixed field blocks, each `name ':' 'N'` (SQL NULL) or `name ':V:' <utf8-byte-length> ':' <value-bytes>`, each terminated by one LF (0x0A).

- **Content envelope** (`BESTCOACH-REPORT-CONTENT-V1`), exactly fourteen blocks: `content_version` (decimal `1`); `todays_strength`; `next_focus`; `practice_suggestion`; `session_takeaway`; then the nine ratings named by `dimension_code` label with the `competency_rating` enum label as value (e.g. `body:V:6:secure`).
- **Wording envelope** (`BESTCOACH-REPORT-WORDING-V1`), exactly five blocks: `content_version` (decimal `1`); `todays_strength`; `next_focus`; `practice_suggestion`; `session_takeaway`. **The two envelopes are domain-separated and share no preimage**, so neither can ever be confused for or substituted for the other.
- **Rating order is pinned to a hard-coded nine-element list inside the content serializer**, in `dimension_code` enum declaration order: `body`, `emotion`, `speech`, `tonality`, `eye_contact`, `vocal_projection`, `emotional_expression`, `sentence_flow`, `audience_awareness`. It is **deliberately not** keyed to `assessment_dimensions.sort_order`, an ordinary mutable column protected by no trigger — a future display-ordering change would silently invalidate every historical hash. The hard-coded order happens to equal the seeded `sort_order` 1–9; that is an observation, not the authority. **Fixed arity:** `p_ratings` must be a nine-element array with no NULL element; any other length, or a NULL array, **raises**.
- **Bytes are hashed exactly as stored.** Panels are persisted byte-verbatim; **no Unicode normalization, trimming, or case folding is applied on the write path or either hash path**, at any point. Length-prefixing makes raw bytes safe regardless of content.

**`content_hash` is a content identity, not an address.** The address of a version is its `id`. Spec §20's "approved content recoverable by hash" is satisfied by **verifiability** — given a version id, its stored content recomputes to its stored hash — not by hash→row lookup, which is deliberately non-unique: a T12 clone initially carries its source's hash, and a management wording edit that reverts text can legitimately reproduce an earlier hash. **No uniqueness constraint is placed on `content_hash`**, and none is implied anywhere. `revision_number`, identifiers, checklist state, internal notes, lineage and approval metadata are excluded: v3 §23 assigns *by whom* and *when* to the approval rows and the audit actor triple, and the hash covers exactly the reviewable substance.

**Computed at:** every version INSERT, inside the same transaction, from values the RPC already holds. **Ratified statement order for every version-creating path**, because the FK direction admits no other: (1) read/receive the four panels and the nine ratings; (2) compute both hashes from those arguments; (3) INSERT the `report_versions` row with `content_hash` and `content_hash_version` populated; (4) INSERT the nine `report_version_ratings` rows; (5) INSERT the all-false checklist row **where the creating operation is a trainer operation** (§3.3). Argument-purity is a hard requirement, not a style choice: `report_version_ratings` rows are FK children and cannot exist until after the version row is INSERTed, so a serializer that resolved ratings by reading the table would hash an empty rating set, and no ordering, DEFAULT or deferral could repair it while `content_hash` is NOT NULL.

### 5.1 Posture, mechanism and the entry-point inventory

**Shared posture (the fifteen entry points and the authorization helper):** **`LANGUAGE plpgsql` for every one of the sixteen — no `LANGUAGE sql` body is authorized anywhere in Step 7I** (tightened at Step 7I1D-R2; the earlier "reads may be `sql`" is withdrawn). Owner `postgres` under the P-1 fail-closed guard, `SECURITY DEFINER`, `SET search_path = ''`, fully schema-qualified references, no dynamic SQL. **The two serializers are the exception on rights, not on language**: also `LANGUAGE plpgsql` (§4.6), but `IMMUTABLE` and **`SECURITY INVOKER`**, `SET search_path = ''`, owner `postgres` — invoker rights are safe there precisely because their only callers already run as `postgres`.

> **Why the language is now pinned rather than permitted to vary.** A `LANGUAGE sql` or SQL-standard `BEGIN ATOMIC` body is **parse-analyzed at `CREATE FUNCTION` time** whenever `check_function_bodies` is on, which is the default; a `plpgsql` body defers parse analysis of its SQL expressions to first execution. That difference is decisive for a function containing a `'trainer_approved'` literal — and RPC-15, whose whole purpose is to select on `trainer_approved`, is precisely a read, i.e. exactly what the withdrawn wording would have permitted to be `sql`. The A-040 migration split already removes the hazard by committing the label first, but pinning the language removes the second, independent way to reintroduce it. See U-7I-18.

**EXECUTE — the fourteen grants and four exclusions of §5.0.** One signature-qualified `REVOKE ALL ON FUNCTION … FROM PUBLIC, anon, service_role, authenticator` line and one signature-qualified `GRANT EXECUTE … TO authenticated` line **per granted function**, in the Step 7G block form (never an aggregate or unqualified statement, which would be ambiguous under any future overload). The **four** zero-EXECUTE functions instead receive a single signature-qualified `REVOKE ALL … FROM PUBLIC, anon, authenticated, service_role, authenticator` and **no `GRANT` of any kind** — the Step 7H audit pattern, which adds `authenticated` to the revoke list. **§5.0 is the sole authority for these counts.**

**R-27 — `report_store_draft` is internal/server-only (ratified at 7I1B-R0, resolving B-7I-5).** AI draft storage holds **no `authenticated` client EXECUTE**. This closes the standing grounding-bypass surface: `CLAUDE.md` §4 non-negotiable 1 forbids ever shipping a path where AI output reaches the trainer without grounding, and a client-executable RPC accepting four arbitrary text fields is exactly such a path once granted, permanently and reachable from `lib/supabase/browser.ts`. **The later AI checkpoint owns the trusted generation-completion channel** that invokes it — a `postgres`-owned `SECURITY DEFINER` caller, whose contract that checkpoint defines and whose grounding obligation it carries. Step 7I's acceptance tests invoke it as `postgres` and additionally prove **zero** client EXECUTE from the catalogue. **Consequence, recorded:** until the AI checkpoint defines that channel, no client-reachable path stores a draft, so the `drafting → draft_ready` arc is exercisable in Step 7I only by tests. That is the intended posture, not a gap.

**Why `authenticated` EXECUTE is correct for the rest and does not contradict Step 7E.** A-030's "no client RPC `EXECUTE`" bullet sits under the heading "**Step 7E posture:**" and is checkpoint-scoped, not standing. The standing rule presupposes client EXECUTE on definer RPCs: "governed mutations use reviewed, constrained `SECURITY DEFINER` RPCs **when they are introduced**… a caller holding no DML **cannot** perform a governed write through a `SECURITY INVOKER` function." `CLAUDE.md` §6.1 restates the Step 7E posture with the same explicit scoping.

**Why RLS does no work inside these functions — the accurate mechanism.** It is **not** that `SECURITY DEFINER` bypasses RLS; it does not. The RPCs execute as `postgres`, which **owns** every table they touch, and no table in this database carries `FORCE ROW LEVEL SECURITY`. A table owner bypasses RLS unless RLS is forced. **This depends on ownership, not on the `SECURITY DEFINER` keyword**, and two standing invariants follow: (a) `FORCE ROW LEVEL SECURITY` must not be added to any report-lifecycle table without re-deriving every RPC's access; and (b) if A-030's deferred U-22 restricted `NOLOGIN` definer owner is ever adopted, the new owner is *not* the table owner and *not* `BYPASSRLS`, so every RPC would become fully RLS-evaluated against zero policies and silently return and write nothing — fail-closed, but a total functional break. Because RLS is inert inside them, **every authorization check must be explicit**: each entry point resolves and authorizes its caller internally and fail-closed, and `audit_append_event` then independently re-validates the actor triple as defence in depth.

**Threat-model note.** An empty `search_path` means an unqualified name resolves to nothing (only `pg_catalog` is implicitly searched), so no `pg_temp` object and no caller-created function can shadow a referenced object; combined with Step 7E's `REVOKE CREATE ON SCHEMA public FROM PUBLIC`, a client cannot create a shadowing candidate in the first place.

**Audit atomicity.** Every mutation RPC **that emits an event** calls `audit_append_event` **in the caller's transaction — the same transaction as its business write** — after all guards pass and the business write succeeds, and before returning. `report_update_checklist` emits no event, so "every mutation RPC appends" is deliberately *not* claimed.

**R-14 — lock-version discipline.** **Every committed aggregate mutation bumps `reports.lock_version` by exactly 1** — including the two status-preserving mutations, T5 and T9, which move `current_cycle_version_id` and are therefore aggregate changes. Management Approve & Submit performs two transitions and bumps **twice**. `report_update_checklist` validates the caller's expected `lock_version` without bumping it. Every stale-CAS acceptance test's expected values derive from this rule.

**Note on A-030's "SECURITY INVOKER remains the default for reads":** all three read RPCs must be `SECURITY DEFINER` because `authenticated` holds zero SELECT on all report tables — the same "a caller holding no privilege cannot act through an invoker function" logic A-030 uses to mandate definer mutations. This is a documented, source-justified deviation, not a silent one.

**R-28 — actor resolution is role-specific and fail-closed on both sides.** Each RPC resolves its own `actor_membership_id` under definer rights: a **trainer** entry point resolves *the single active `trainer` membership of `app_current_account_id()` in the report's centre*; a **management** entry point resolves *the single active `management` membership* of the same account in the same centre. Both fail closed on zero or more than one match, using the `HAVING count(*) = 1` discipline `app_current_account_id` already sets. `centre_memberships_one_active_management_per_centre_idx` guarantees the management side resolves uniquely (A-015's "one named management account" made physical). `audit_append_event` then re-proves the same triple against `accounts` and `centre_memberships` independently.

**Inventory adjudication (R-15).** Alternatives compared: **(a)** one generic `report_transition(p_action text, …)` dispatcher — rejected: dynamic dispatch obscures per-transition guards and signatures, weakens static review, and invites unregistered actions; **(b)** folding trainer approval into management Approve & Submit — rejected outright: they are performed by different actors, at different times, with different gates, and merging them would destroy the two-stage guarantee; **(c)** a single `report_management_action(p_action …)` covering edit/return/submit — rejected for the same dispatcher reasons, and because the three have entirely different write sets; **(d)** deferring the drafting arcs to the AI checkpoint — rejected: the 7H baseline assigns E1–E3 to 7I, and the transitions are pure CAS state changes exercisable without an LLM. **(e)** The chosen inventory is the minimum that covers every ratified transition, the three mandated read models, and no generic CRUD: there is no `report_delete`, no `report_update`, no version CRUD, no checklist-row CRUD, no approval CRUD, and no standalone correction-request CRUD.

## 6. Operation protocols (R-17)

Each protocol below runs inside **one database transaction**. Every confirmation modal is a UX safeguard only — the server enforces everything below regardless of how the RPC is reached.

### 6.1 Trainer approval — RPC-8 (T7 / T8)

1. **Re-read authoritative state:** lock the `reports` row (`SELECT … FOR UPDATE`); re-read status, `lock_version`, `current_cycle_version_id`.
2. **Revalidate live authorization:** active trainer membership + active session assignment (`app_trainer_reaches_session`), attendance `present`, active enrolment, session start reached (R-9).
3. **Domain check, before CAS:** reject any `p_expected_status` outside `{'draft_ready','needs_edit'}` with the authored illegal-transition error. Without this the parameter's type admits all eight labels, and a caller could satisfy CAS against a state the transition does not serve, dying on a constraint rather than on a transition guard.
4. **CAS:** `status = p_expected_status` AND `lock_version = p_expected_lock_version` AND `current_cycle_version_id = p_expected_version_id`, all compared with `IS NOT DISTINCT FROM` so a NULL expectation can never be read as a match. Any mismatch ⇒ authored stale-state error, nothing written.
5. **Prior-approval gate (R-7a):** reject with a **named authored error** if a `report_version_approvals` row already exists for `p_expected_version_id` with role `trainer`. This is what makes T8-after-a-return fail as a *transition guard* rather than as a raw primary-key violation, and it is the only reason the arc has a deterministic authored failure in a state §3.2 declares legal. **After `T7 → T10` every other gate in this protocol succeeds against the frozen candidate — the domain check, the CAS, the all-true frozen checklist, the nine snapshots and the content hash — so this step is the sole barrier, and it is proven by the dedicated negative test T7I-75.**
6. **Checklist gate:** re-read all three `report_version_checklist_progress` booleans **for exactly `p_expected_version_id`**; all three must be true. **A missing checklist row is a failure, not a pass** — it means the candidate is a management-authored version, which can never be trainer-approved. **This gate is proven by a dedicated negative test for each boolean individually and for all three together (T7I-66); it is not proven by any positive-path test.**
7. **Snapshot completeness:** exactly nine `report_version_ratings` rows for that version.
8. **Content-hash verification:** recompute the §4.6 content hash from the stored version content and assert it equals both the stored `content_hash` **and** `p_expected_content_hash` — the caller-supplied hash proves the trainer approved *this exact text*, closing the stale-render window between the trainer's screen and the database.
9. **Trainer approval provenance:** INSERT the `report_version_approvals` row — PK (version id, `trainer`); checklist snapshot copied; CHECK forces all-true; approver membership and **`approver_role = 'trainer'` supplied explicitly, never defaulted** (A-040 drops the column default precisely so an omission fails loudly). **This is the freeze point (A-028).**
10. **Correction-request resolution:** if an `open` `report_correction_requests` row exists for this report, set `status='resolved'`, `resolved_at = now()`, the resolving trainer membership and role, and `resolving_version_id = p_expected_version_id`. **Only an `open` row is ever touched** — a previously `resolved` row is immutable and is never re-resolved, re-dated or re-pointed by a later cycle (T7I-72).
11. **Transition:** update `reports` to `trainer_approved`, `lock_version + 1`; append one `report.state_changed` (`p_expected_status → trainer_approved`) with payload: version id, `content_hash`, the three checklist booleans, and the resolved correction-request id where one was resolved.
12. **Outbox insertion point (A-039 trigger 1):** management notification is owed. **The outbox row belongs HERE, inside this transaction** — the notifications checkpoint will replace this RPC to add that single INSERT at this clearly-marked location, so the row commits with the transition or not at all. **Step 7I creates no notification object, no outbox table and no outbox row** (§10.1).
13. Return; COMMIT. **Only now has the transaction succeeded** — every "succeeded" claim in this protocol refers to this point, not to any earlier step.

**Proofs:** trainer approval publishes nothing — no pointer moves, no submission metadata is written, and the parent read still resolves through an unmoved `latest_submitted_version_id`. A double-click fails CAS on `status = 'trainer_approved'`; even a pathological re-entry dies on the approval PK.

### 6.2 Management wording edit — RPC-9 (T9)

1. Lock the `reports` row; re-read status, `lock_version`, `current_cycle_version_id`.
2. **Revalidate live authorization:** a single active `management` membership of the report's centre (R-28). A trainer or parent context is rejected with the authored role error.
3. **CAS:** `status = 'trainer_approved'` AND `lock_version = p_expected_lock_version` AND `current_cycle_version_id = p_expected_version_id`.
4. **Lineage gate:** resolve the trainer-approved source of `p_expected_version_id` (§4). It must exist and must carry a trainer approval row. **No source, no edit.**
5. **Wording-hash verification:** recompute `report_wording_hash_v1` from the current candidate's stored panels and assert it equals `p_expected_wording_hash` — management edits *the text it was shown*.
6. **Field allow-list:** the RPC's signature accepts **only** the four parent-facing panels as content. It has **no caller-supplied parameter** for a rating, an observation, an attendance row, an evidence object, a trainer note, a checklist row, an approval row, `revision_number`, lineage, authorship or submission metadata, and it executes **no statement writing** `observations`, `observation_ratings`, `attendance`, any evidence object, `report_version_checklist_progress` or `report_version_approvals`. **The allow-list is the signature, not a runtime filter.**
   > **Precision, corrected at Step 7I1D-R2.** An earlier draft of this step said the RPC "executes no statement writing … a rating", which **contradicted step 7 and the §3.2 write column**: T9 *does* INSERT nine `report_version_ratings` rows for the new version. The accurate statement is the one above — management supplies **no rating value**, and the nine snapshots are copied **verbatim from the source version** by the server. The distinction matters to the 7I2B static reviewer, who would otherwise flag the mandatory INSERT as a violation of this step.
7. **INSERT the new version:** the four supplied panels; **nine rating snapshots copied verbatim from the source version**; both hashes recomputed; `derived_from_version_id` = the prior candidate; `trainer_approved_source_version_id` = the resolved trainer-approved source; `authored_by_*` = the acting management membership and `'management'`. **No checklist row is created** (§3.3).
8. **Transition:** update `reports` — `current_cycle_version_id` ← the new version, `lock_version + 1`, **`status` unchanged at `trainer_approved`**; append one `report_version.created`. **No `report.state_changed` is appended, because no state changed.**
9. Return; COMMIT.

**Proofs:** the trainer-approved version's content, hashes, nine snapshots, checklist evidence and trainer approval row are never written by this path and remain byte-identical. Ratings cannot change, because they are copied from the source and the RPC accepts no rating parameter. Nothing becomes parent-visible, because `latest_submitted_version_id` does not move.

### 6.3 Conditional return-to-trainer — RPC-10 (T10)

1. Lock the `reports` row; re-read status, `lock_version`, `current_cycle_version_id`.
2. **Revalidate live authorization:** a single active `management` membership of the report's centre.
3. **CAS:** `status = 'trainer_approved'` AND `lock_version = p_expected_lock_version` AND `current_cycle_version_id = p_expected_version_id`. **The return is legal from `trainer_approved` and from nowhere else** — management cannot return a report it has already submitted, nor one the trainer has not yet approved.
4. **Issue-scope gate:** `p_issue_scope` must be one of the ratified vocabulary values; `p_dimension_code` must be non-NULL when the scope is `rating` and NULL otherwise; `p_reason` must be non-blank and within the ratified bound.
5. **Duplicate gate:** the partial unique index on `status = 'open'` rejects a second open request for the report; the violation is mapped to an authored error.
6. **INSERT the correction request** with the report, the exact version under review, the scope, the optional dimension, the reason, the acting management membership role-pinned to `management`, `requested_at = now()`, and `status = 'open'`.
7. **Transition:** update `reports` to `needs_edit`, `lock_version + 1`. **No version is created and no version content is written** — the return records a request; it never performs the correction. **`latest_submitted_version_id` is not touched.**
8. **Audit:** append one `report.state_changed` (`trainer_approved → needs_edit`) whose payload carries the **correction-request id**, the issue scope, the affected `dimension_code` where present, and the version id — **and never the reason text** (§10, B-7I-4).
9. **Outbox insertion point (A-039 trigger 2):** the actively assigned trainer is owed a notification. **The outbox row belongs HERE, inside this transaction**, at this clearly-marked location, for the notifications checkpoint to add. **Step 7I creates no notification object, no outbox table and no outbox row.**
10. Return; COMMIT. **The transaction has succeeded only at this point.**

**Proofs:** management alters no assessment data — the RPC writes only `reports` and `report_correction_requests`, and management holds no DML anywhere. The trainer-approved source version is untouched and its trainer approval row remains valid, so if the trainer's correction later reproduces identical content the lineage is still sound. **The report remains unavailable to parents:** the canonical pointer did not move, so a never-submitted report still resolves to nothing and a previously submitted one still resolves to its previous canonical version — never draft content, and **never any disclosure that a correction cycle is underway** (§8.3).

### 6.4 Management Approve & Submit — RPC-11 (T11)

One user action, one RPC, **one database transaction**, two transitions, two audit events.

1. **Re-read authoritative state:** lock the `reports` row; re-read status, `lock_version`, `current_cycle_version_id`.
2. **Revalidate live authorization:** a single active `management` membership of the report's centre (R-28). This is the *live centre authorization* A-037 requires — never a token claim, never UI state.
3. **CAS:** `status = 'trainer_approved'` AND `lock_version = p_expected_lock_version` AND `current_cycle_version_id = p_expected_version_id`, with `IS NOT DISTINCT FROM`. **This is the obsolete-version gate**: a management approval of anything other than the report's current candidate cannot pass.
4. **Trainer-approval lineage gate:** resolve the trainer-approved source of the final version (§4) — the final version itself when it carries a trainer approval row, otherwise its `trainer_approved_source_version_id`. That source must exist and must carry a trainer approval row. Because step 3 already proved the final version is the report's **current** candidate, the resolved source is the **current** lineage root by construction — a stale or superseded source cannot reach this gate. **This is the structural implementation of "management submission without trainer approval must be prevented."** It reads an existing trainer approval; it never creates, copies or infers one (R-12a).
5. **Rating-parity gate:** the final version's nine `report_version_ratings` rows must match the trainer-approved source's nine `(dimension_code, rating)` pairs **exactly**. This independently re-proves that no wording edit mutated or impersonated a rating, even if an implementation error occurred upstream.
6. **Snapshot completeness:** exactly nine `report_version_ratings` rows for the final version.
7. **Content-hash integrity:** recompute the §4.6 content hash from the final version's stored content and assert it equals the stored `content_hash`. A mismatch is a **data-integrity anomaly**, distinct in code and shape from a caller mismatch.
8. **Wording-hash proof:** recompute `report_wording_hash_v1` from the final version's stored panels and assert it equals `p_expected_wording_hash` — management submits *the exact text it reviewed*. **The content hash is never returned to, nor accepted from, management** (R-26).
9. **Management approval provenance:** INSERT the `report_version_approvals` row — PK (final version id, `management`); approver membership + role-pinned `management`; `approved_at = now()`; checklist snapshot copied from the **trainer-approved source's trainer approval row**, so the all-true CHECK is satisfied by truthful evidence (§3.3).
10. **Transition 1:** update `reports` to `approved`, `lock_version + 1`; append `report.state_changed` (`trainer_approved → approved`) with payload: final version id, its `content_hash`, the trainer-approved source version id, and the three checklist booleans.
11. **Transition 2:** update `reports` to `submitted`, `lock_version + 1`, `latest_submitted_version_id` = the final version; write-once `submitted_at = now()`, `submitted_by_membership_id`, **`submitted_by_role = 'management'`** on the version row; append `report.state_changed` (`approved → submitted`), same version id and `content_hash`.
12. **Outbox insertion point (A-039 trigger 3):** linked parents are owed a notification. **The outbox row belongs HERE, inside this transaction**, at this clearly-marked location, for the notifications checkpoint to add. **Step 7I creates no notification object, no outbox table and no outbox row.**
13. Return; COMMIT. **The transaction has succeeded only at this point** — the notification *record* and its delivery are created **after** this commit, by a separately driven worker reading committed outbox rows (§10.1).

**Proofs the design provides:**

- **No `approved`-without-`submitted` residue:** both transitions and both appends share one transaction; any failure at any step aborts everything — status is either `trainer_approved` or `submitted` after any single call, **never a committed `approved`** (T7I-20).
- **No submission without trainer approval:** step 11 cannot be reached without step 4 succeeding in the same transaction, and the approval rows' CHECK makes unproven approval unrepresentable.
- **No management approval of an obsolete version:** step 3's three-way CAS plus step 8's wording proof.
- **No silent transfer of trainer approval to changed content:** approval is keyed to a version id and carries that version's content hash; every content change creates a **new** version with a **new** hash and **no** trainer approval row of its own, and step 4 resolves lineage explicitly rather than assuming it.
- **No parent visibility before submission:** `latest_submitted_version_id` moves only at step 11.
- **No management change to assessment data:** management's only content mutation is §6.2's wording edit, whose signature has no rating, observation, attendance, evidence or note parameter; step 5 re-proves parity here.
- **Return-to-trainer cannot be bypassed for assessment-level corrections:** every path that changes a rating runs through `observation_ratings` (assessment scope) and then a trainer save, and management has no write path to either.
- **Exactly two lifecycle audit events, provably adjacent:** the first `audit_append_event` call takes the per-centre head row lock (`FOR UPDATE`), which PostgreSQL holds until transaction end; the second call re-reads its own uncommitted head update and allocates the next sequence number. The two events are therefore **dense-consecutive (`n`, `n+1`) with direct hash linkage, and no foreign event can interleave** on that centre's chain. (Corollary, stated for review honesty: the centre's audit appends serialize behind this transaction for its remaining duration — acceptable at MVP scale.)
- **Double-click cannot double-publish:** the second call fails CAS on `status = 'submitted'`; even a pathological re-entry dies on the management approval PK.

### 6.5 Management pre-submission read — RPC-15 (R-32, added at Step 7I1D-R2)

**This protocol did not previously exist, and its absence was the design's most serious defect.** RPC-15's shape was specified while its **status precondition was specified nowhere** — not in §5.1, not in §6, not in §8.2. §8.2 asserted the *outcome* ("Management never receives pre-trainer-approval draft content") with no mechanism behind it, and no test provoked it. Because RPC-15 returns the content of **`current_cycle_version_id`**, and that pointer names the trainer's **live working version** whenever the report is `drafting`, `draft_ready` or `needs_edit`, an implementation faithful to the old text would hand management an un-approved draft — reachable in the **ordinary** two-stage flow, immediately after any return (T10), not only by a bypass. That is a direct violation of A-038, of A-038's per-row gating rule, and of `CLAUDE.md` §6.

1. **Resolve the report** for `(p_class_session_id, p_student_id)`. No report ⇒ the authored **"not available"** outcome.
2. **Revalidate live authorization:** a single active `management` membership of the report's centre (R-28). Any other role, or zero/ambiguous membership ⇒ the same authored not-found/not-permitted outcome, indistinguishable from "no such report" (§8.6).
3. **Status gate — the ratified branch table. There is no default branch that returns content.**

| Aggregate status | Returned |
|---|---|
| `trainer_approved` | The **final-review candidate**: status, `lock_version`, `current_cycle_version_id`, the candidate's **four parent-facing panels**, the computed **`wording_hash`**, `submitted_at` (NULL unless a previous cycle published), and the open correction request's **scope and status** if any |
| `submitted` | The **submitted** shape: status and the version named by `latest_submitted_version_id` — its **four panels** and `submitted_at`. **`wording_hash` is NULL** (there is no candidate to prove a render against) and no `current_cycle_version_id` is returned |
| `incomplete` · `observation_saved` · `drafting` · `draft_ready` · `needs_edit` | The authored **"not available"** outcome. **Zero panels. No version id. No `wording_hash`. No `lock_version`.** Not an empty string, not a NULL-filled row of the candidate shape — the unavailable outcome |
| no report row at all | The same authored **"not available"** outcome, byte-indistinguishable from the row above |

4. **Never, at any status:** ratings, `content_hash`, `revision_number`, checklist internals, approval internals, trainer notes, AI history, audit rows, or the correction **reason** text (§8.6).

**Proofs:** the pre-approval statuses are exactly the five A-038 names as exposing no report content to management; the `needs_edit` case closes the return-cycle hole specifically; and the unavailable outcome is identical whether the report is mid-draft, returned, or absent, so management learns nothing about workflow state it is not authorized to act on. Proven by T7I-63.

### 6.6 Canonical read — RPC-13 (R-33, added at Step 7I1D-R2)

**RPC-13's trainer and management predicates were never specified.** §8.1 scoped the live-assignment re-check to "every trainer mutation RPC and RPC-14"; §8.2 scoped the management re-check to RPC-9, RPC-10, RPC-11 and RPC-15. RPC-13 was **absent from both**, and only its parent branch was written down. RPC-13 is `SECURITY DEFINER`, holds `authenticated` EXECUTE, and RLS is inert inside it (§5.1) — so the internal predicate is the **only** boundary, and an implementer with nothing to implement would have left two of three branches ungated. The session and student ids needed to exploit that are readable: Step 7G grants `authenticated` SELECT on `class_sessions` and `students`.

1. **Resolve the report** for `(p_class_session_id, p_student_id)`; resolve the caller's account (`app_current_account_id()`), fail-closed on NULL.
2. **Dispatch on the caller's single active membership in the report's centre**, resolved live and fail-closed on zero or more than one (R-28):
   - **`trainer`** ⇒ require **`app_trainer_reaches_session(report.class_session_id)`** — the live class-session assignment, identical to the predicate every trainer mutation RPC and RPC-14 already use. A trainer assigned to a different session is denied.
   - **`management`** ⇒ require a **single active `management` membership of the report's centre**, identical to RPC-9/10/11/15. Wrong-centre management is denied.
   - **`parent`** ⇒ require **`app_parent_reaches_student(p_student_id)`** — an active `parent` membership owning an active link to that student.

3. **Resolve content exclusively through `latest_submitted_version_id`.** NULL ⇒ the authored **"not available"** outcome, for **every** role — a trainer-approved-but-unsubmitted version is unreachable here by construction, not by a status test.
4. **Return the four panels and `submitted_at`, and nothing else** (§8.6, R-19a) — one shared canonical shape for all three roles (A-021).

**Proofs:** every branch has a named live predicate; no branch defaults to permit; the unauthorized outcome is identical whether the target exists or not; and no role can reach an unsubmitted version, because the resolution path names only the canonical pointer. Proven by T7I-65.

## 7. CAS, idempotency and concurrency (R-18)

Per the 7H baseline §5.3, the duplicate gate is owned by **each governed RPC** — there is **no audit-level idempotency key**, and the audit layer records only accepted operations. Every gate fires **before** any audit append.

**R-18a — the aggregate mutex rule.** The `reports` row is the mutex for the entire report aggregate. **Every mutation RPC acquires it as its first statement** — `SELECT … FROM public.reports WHERE id = p_report_id FOR UPDATE`, or the guarded CAS `UPDATE` itself where the RPC reads no aggregate-owned state beforehand — and performs **every** read and write of `report_versions`, `report_version_ratings`, `report_version_checklist_progress`, `report_version_approvals` and `report_correction_requests` for that report only while holding it. Two consequences make this load-bearing rather than stylistic:

- A bare guarded `UPDATE … WHERE id = $r AND status = $expected AND lock_version = $expected` **is** a correct compare-and-set under READ COMMITTED: a concurrent writer makes the statement block on the row lock and then re-evaluate its `WHERE` against the newly committed row version, so a bumped `lock_version` yields zero matched rows and an authored error. That is sufficient **only** for an RPC that reads nothing before writing.
- It is **not** sufficient for any RPC that reads aggregate-owned state first — which includes RPC-7 (§3.3) and **every one of RPC-6, RPC-8, RPC-9, RPC-10 and RPC-11**, each of which reads versions, snapshots, checklists, approvals or lineage *between* the lock and the writes. Without the explicit lock those reads run on a snapshot a concurrent writer can invalidate, and §6's serialization proofs collapse.

**R-18b — expected-status is a parameter only where a transition has two legal origins.** RPC-2, RPC-3, RPC-5 and RPC-12 each serve exactly one arc, so their from-status is fixed inside the RPC and is **not** a caller argument. **RPC-6 and RPC-8 accept `p_expected_status`**, because each has two legal origins (`draft_ready` and `needs_edit`). **RPC-9, RPC-10 and RPC-11 do not**, because each has exactly one legal origin (`trainer_approved`) — this is a change from the superseded design, where the approve RPC was the only two-origin operation, and it follows mechanically from the same rule. Acceptance tests must therefore establish a wrong from-status by *placing the report in it*, never by passing a different parameter value.

| Operation | Gate | Duplicate / race killed |
|---|---|---|
| RPC-1 create | `reports_session_student_key` + `reports_observation_key` unique violations → authored error | double-click create, two tabs |
| RPC-2, 3, 5, 12 | `UPDATE public.reports SET … WHERE id = $r AND status = $expected AND lock_version = $expected` — 0 rows ⇒ authored error | repeat calls, stale tabs, concurrent editors |
| RPC-6 save edit | CAS on (status ∈ two origins + lock_version + current-version id) | stale editor; two tabs saving different text |
| RPC-7 checklist | validated (not bumped) `lock_version` + expected current-version id + status ∈ {draft_ready, needs_edit} + **Gate A: no approval row on the target version** + **Gate B: the target version is trainer-authored** — **all under the row lock** (§3.3) | checklist-toggle-vs-save race; toggle against a superseded version; **toggle against a frozen trainer-approved version after a management return**; **toggle against a management-authored version that has no checklist row** |
| RPC-8 trainer approve | CAS (status + lock_version + current-version id) + `p_expected_content_hash` + trainer approval PK | stale approve after edit; regenerate-vs-approve; double-click |
| RPC-9 wording edit | CAS on `trainer_approved` + current-version id + `p_expected_wording_hash` + lineage gate | management editing text a return already superseded; two management tabs |
| RPC-10 return | CAS on `trainer_approved` + the `open` partial unique index | double-click return; two open requests |
| RPC-11 approve & submit | CAS on `trainer_approved` + current-version id + wording proof + lineage + parity + management approval PK | stale submit after a wording edit; submit-vs-return race; double-click; replayed request |
| RPC-4 repeat call | CAS on `status='drafting'`, plus the already-holds-a-version guard (R-11a) | late duplicate AI result discarded |
| Repeat submission | CAS fails on `status='submitted'`; management approval PK backstop | publication retry is safe: retry after an ambiguous failure re-reads state; if the first attempt committed, the retry fails CAS cleanly with no second effect |
| Transaction rollback | single-transaction rule: business rows, checklist writes, approval rows, correction-request rows, audit events and head update all roll back together | no partial outcome is ever observable |

**Operation-level idempotency where no natural CAS exists:** every 7I mutation has a natural CAS or uniqueness gate — no client-supplied idempotency key is needed. The `ai_jobs` keyed idempotency of spec §24 belongs to the AI checkpoint and rides on `observations.lock_version` (R-21a).

**The new two-actor races, and why each is safe.** All **six** resolve on the same `reports` row lock plus CAS, so exactly one writer wins and the loser fails with an authored stale-state error having written nothing: **(a)** management returns while the trainer is mid-save — the trainer holds `draft_ready`/`needs_edit`, management requires `trainer_approved`, so at most one is legal at any instant; **(b)** management submits while management returns (two management sessions) — both require `trainer_approved`, the loser's `lock_version` no longer matches; **(c)** management wording-edits while management submits — same shape, and the submitter's wording-hash proof additionally fails; **(d)** management submits while the trainer reopens a *previously* submitted report — different origin statuses, mutually exclusive; **(e)** two management sessions double-submitting — the second fails CAS on `status='submitted'`, with the management approval PK as backstop; **(f)** **management wording-edits while management returns** — added at Step 7I1D-R2, and genuinely admissible rather than hypothetical: T9 and T10 are the two management operations that share the single origin `trainer_approved`, so two management sessions can legally attempt them at the same instant. The winner bumps `lock_version`; the loser fails CAS having written nothing. Order matters to the outcome but not to safety — an edit that wins leaves a new candidate the return would then have to be re-issued against, and a return that wins leaves `needs_edit`, which T9 does not serve. **This set is now exhaustive over the pairs of operations that share a legal origin.** Proven by T7I-61.

## 8. Authorization and visibility (R-19)

All checks are live database checks inside the definer RPCs — never JWT claims, never UI state. Deny-by-default is not weakened: no table grant, no policy, and no `service_role` ACL entry is added by Step 7I; the correction-request table receives **zero client privileges and RLS enabled with zero policies**, exactly like the five report tables; the only new client-reachable surface is EXECUTE on **fourteen** functions — the fourteen `authenticated`-callable RPCs, and nothing else (§5.0 as recalculated at Step 7I1D-R2: `app_parent_reaches_student` is now owner-only, R-31).

**Every one of those fourteen is reachable by any authenticated session of any role**, so **role is a predicate inside each function, never a property of the grant**. That is why §8.1–§8.3 must name a predicate for **every** (role, function) pair rather than only for the pairs a UI would exercise, and why the acceptance contract carries a **complete three-role denial matrix** (T7I-24, T7I-67) rather than a two-role one.

### 8.1 Trainer

- Must be the **live assigned trainer** for the report's class session: `app_trainer_reaches_session(report.class_session_id)` re-checked inside **every** trainer mutation RPC, **RPC-14, and RPC-13's trainer branch** (§6.6 — RPC-13 was previously missing from this list, and that omission left its trainer branch with no specified predicate at all) — assignment removal revokes access on the next call.
- May create and progress only through the ratified trainer transitions; may not bypass the checklist, attendance, enrolment, future-session or state guards.
- **May not act past their own approval.** Once the report is `trainer_approved`, no trainer RPC has a legal origin — the trainer cannot un-approve, edit, withdraw, or submit. The only routes onward are management's.
- Reads full working state through RPC-14, **including any open correction request and its reason** — the trainer must see what to fix.

### 8.2 Management

- Centre-scoped: a **single active `management` membership** of the report's centre, resolved live (R-28) and re-checked inside RPC-9, RPC-10, RPC-11, RPC-15 **and RPC-13's management branch** (§6.6 — RPC-13 was previously missing from this list too).
- **May: read the final-review candidate (RPC-15) — but only while the report is `trainer_approved`, and the submitted shape only while it is `submitted`; at every other status RPC-15 returns the authored unavailable outcome with zero panels (§6.5).** Read the canonical submitted version (RPC-13); edit parent-facing wording (RPC-9); return the report to the trainer for an assessment-level issue (RPC-10); Approve & Submit (RPC-11).
- **May not: create a report, mark observations saved, request or store a draft, cancel a draft, save a trainer edit, touch the checklist, perform the trainer approval, or reopen a submitted report.** Every trainer RPC rejects a management actor with an authored role error.
- **Management never receives:** pre-trainer-approval draft content — **enforced by RPC-15's status gate (§6.5), not merely asserted here**; internal notes (`observations.observation_notes`, `follow_up_notes`, chips, term-evidence notes), raw per-dimension assessment data in any form, checklist internals, approval internals, AI generation history, audit rows, **the content hash**, `revision_number`, or the correction **reason** text. Status *metadata* breadth (report-status tables on management screens) remains Phase 3 read-projection work, not RPC-15.
- **Management has no write path to assessment substance at all.** It holds zero DML on every table, and no management RPC accepts a parameter for, or executes a statement writing, `observations`, `observation_ratings`, `attendance`, any evidence object, a trainer note, a checklist row, or another role's approval row.

### 8.3 Parent

- Linked-child scoped and **view-only — unchanged and absolute**: RPC-13's parent branch requires `app_parent_reaches_student(p_student_id)` — an active parent membership owning an active link to that student.
- **A parent is denied on every other function Step 7I grants (stated explicitly at Step 7I1D-R2).** `authenticated` EXECUTE is held by any authenticated session regardless of role, so a parent's browser session **can invoke** RPC-1, 2, 3, 5, 6, 7, 8, 9, 10, 11, 12, 14 and 15. Every one of them must reject a parent context with the authored role error — the trainer RPCs and RPC-14 because R-28's trainer resolution finds no active `trainer` membership, RPC-9/10/11/15 because its management resolution finds no active `management` membership, both fail-closed. **This is the "server must reject a parent edit attempt even when the call bypasses the UI entirely" rule of A-021 and `CLAUDE.md` §6, applied to every entry point rather than assumed.** The most dangerous single pair is **parent → RPC-14**, whose working-state shape carries the nine rating snapshots, the `content_hash` and the open correction reason; a linked parent asking about their **own** child passes every relationship check in the system, so only the **role** predicate stands between them and the caught rating-grid leak. Proven by the complete linked-parent denial matrix, T7I-67.
- Only submitted parent-facing content: RPC-13 resolves exclusively through `latest_submitted_version_id`; if NULL, the parent receives the authored "not available" outcome — never draft data, never a trainer-approved-but-unsubmitted version, and **never confirmation that a correction cycle is underway**.
- **A returned report is never parent-readable.** T10 moves no pointer, so a never-submitted report still resolves to nothing and a previously submitted one still resolves to its previous canonical version. There is no status, timestamp or field in RPC-13's return shape from which a parent could infer that management returned the report.
- Never: drafts, internal notes, **any per-dimension rating grid in any form** (RPC-13's return shape excludes `report_version_ratings` entirely), checklist internals, approval internals, correction requests, audit history, content hashes, revision numbers.

### 8.4 Absent student / AI

- **Absent student:** no report may be created or progressed where attendance for (session, student) is not `present` (R-9); a missing attendance row fails closed. The converse invariant — submitted-report attendance cannot flip to `absent` — is owned by the Phase 1 attendance RPC and is **vacuously safe until then**: no client holds attendance DML. The attendance RPC and RPC-1 must share a two-writer proof (lock the attendance row `FOR UPDATE` inside RPC-1's guard) when that checkpoint is designed.
- **AI:** has no portal role, no credential, and — under R-27 — **no client-reachable RPC of any kind**. It cannot approve, submit, publish or choose lifecycle state. The only path to `submitted` is RPC-11, which requires a live management actor; the only path to `trainer_approved` is RPC-8, which requires a live trainer. The AI checkpoint's pipeline will reach RPC-4 through a trusted server-side channel it defines, under the trainer's authenticated action, with grounding governing its content before storage.

### 8.5 Notification recipients (A-039, resolved live)

Recipient sets are resolved from live relationships at the moment the trigger fires, never cached and never taken from a token claim: **trigger 1** → every active `management` membership of the report's centre; **trigger 2** → the actively assigned trainer for the report's class session; **trigger 3** → every parent holding an active `parent_student_links` row for the report's student. **Step 7I resolves and ratifies these rules; it creates no notification record** (§10.1).

### 8.6 Return-shape and error discipline

- **R-19a — RPC-13 returns exactly the four content panels and `submitted_at`. Nothing else.** One shared canonical read model for all three roles (A-021). No ratings, no notes, no approver identity, no checklist, no pointers, no audit fields — **and specifically no `content_hash` and no `revision_number`.**
  - **No content hash reaches any reader other than the trainer** (R-26): the 4⁹ brute-force recovers the exact rating grid from panels + hash.
  - **`revision_number` is never returned by RPC-13 or RPC-15.** It is a dense per-report ordinal, so disclosing it tells a reader exactly how many correction cycles a report has been through — the same class of workflow-internal fact this section forbids disclosing.
  - `submitted_at` is retained: A-028 makes it publication metadata, it is the natural "sent on" date for a reader, and it moves only at T11.
- **RPC-15 returns the management review shape and nothing more, and only at the two statuses that authorize it** (§6.5). At `trainer_approved`: status, `lock_version`, current version id, the four panels, the computed `wording_hash`, `submitted_at`, and the open correction request's scope and status. At `submitted`: status, the submitted version's four panels and `submitted_at`, with a NULL `wording_hash`. **At every other status, and where no report exists, the authored unavailable outcome with zero panels and no version id.** It carries the CAS values management genuinely needs (without which management could only submit blind) and nothing that discloses assessment substance. **The correction request's `reason` is never returned by RPC-15** — management authored it; the field exists for the trainer, and RPC-14 is where it is read.
- No RPC echoes `audit_append_event`'s outputs (`o_event_id`, `o_entry_hash`) to a client.
- Errors are authored, minimal and non-disclosing: an unauthorized caller receives the same "not found / not permitted" outcome whether the target exists or not; CAS conflicts state that the expectation failed, never the conflicting content; no error interpolates row content, hashes of unpublished content, a correction reason, credentials or environment values.

## 10. Audit event mapping (R-21)

Exact implemented registry spellings (7H migration `v_registry`): `report.created` · `report_version.created` · `report.state_changed`. **No registry extension is required or permitted.**

**R-29 — the return-to-trainer uses `report.state_changed`, not a new action.** Alternatives compared: **(a)** reuse `report.state_changed` (chosen) — the return **is** a state change (`trainer_approved → needs_edit`), it matches the standing precedent that approval and submission are also generic state-changed events rather than dedicated actions, and it requires **no change to any committed function**; **(b)** add a `report.correction_requested` action — rejected: the registry is a hard-coded `CONSTANT text[]` duplicated inside **two** applied `SECURITY DEFINER` functions (`audit_append_event` and `audit_verify_chain`), so extending it means replacing both in a new migration, and a partial edit would silently break verification of already-committed rows. The correction request is carried as a **related target and a payload id** on the state-change event, which A-029 explicitly supports. **Consequence:** the audit stream distinguishes a return from any other `needs_edit` entry by its `state_from` (`trainer_approved`) and by the presence of a correction-request related target — both are hash-covered, so the distinction is tamper-evident.

Common to every append: originating RPC per §3.2's audit column; centre partition = the report's `centre_id`; same transaction as the business mutation, after all gates.

**R-30 — audit labels and payloads carry no direct PII (ratified at 7I1B-R0, resolving B-7I-4).** Immutable audit labels and payloads **must not contain child names, initials, account names, emails, phone numbers, or other direct PII**. Targets are identified by **UUID**, and labels are **generic and constant**:

| Target type | Ratified label |
|---|---|
| `report` | `Report` |
| `report_version` | `Report version` |
| `student` | `Student` |
| `class_session` | `Class session` |
| `observation` | `Observation` |
| `report_correction_request` | `Correction request` |

This supersedes the earlier draft's identifying labels (student display name; `"Revision <n>"`; session date) **in writing**, and it is the right default for the strongest reason available: **`audit_events` is append-only by trigger and by zero privilege, `audit_verify_chain` treats any alteration as a break, and 7H §6.4 forbids repair "ever"** — so Step 7I would otherwise be the first checkpoint to write a child's identifying name into a row no erasure mechanism can ever touch, and PDPA erasure is deferred to Phase 4. Intelligibility is not lost: every target carries its UUID, and every referenced row remains resolvable by an authorized reader for as long as the business record exists. **Where a label must be non-NULL by function contract, the generic constant satisfies it.**

**The correction reason is never placed in an audit event.** The event carries the correction-request **id**, its `issue_scope`, and the affected `dimension_code` where present — closed vocabulary values and a UUID, all non-identifying. The reason prose lives in `report_correction_requests`, an ordinary application row.

**Payload discipline — three enforcement layers, not conflated.**

- **Function-enforced** (`audit_append_event`, which hard-raises): `p_payload` must be a JSON object; it must **not** contain the reserved key `related_targets`; `p_target_type` must be non-blank; `p_target_label` must be non-NULL; every element of `p_related_targets` must be an object carrying **exactly** the three keys `target_type`, `target_id`, `target_label`, with `target_type` a non-blank string, `target_label` a string, and `target_id` a uuid string or JSON null.
- **Convention-enforced by 7I review and tests only:** lowercase canonical UUID strings, UTC `YYYY-MM-DDTHH:MM:SS.ffffffZ` timestamps, integers and fixed-scale decimals only, no floats.
- **Unenforced at every layer — the state triple.** `audit_append_event` performs no validation of `p_state_domain`/`p_state_from`/`p_state_to`, `audit_events` carries no CHECK on them, and `audit_verify_chain` does not inspect them. A partial triple would be silently hashed into permanent evidence. Step 7I therefore builds the triple through **one reviewed textual convention, written identically at every emitting call site**, and proves the emitted shape by acceptance test rather than by trusting the database. **Stated precisely at Step 7I1D-R2, because the earlier wording ("one shared internal construction … so they cannot diverge") implied a shared SQL function that the §5.0 census does not contain and the 7I2A deliverable list does not create.** It is **not a function**: adding one would make the migration create **nineteen** functions and would fail T7I-2's own `28`-function assertion at apply time. **The "cannot diverge" claim is therefore withdrawn** — divergence is prevented by review plus test, not by structure, and the same is true of the trainer-approved-source resolution rule of §4, which is likewise inlined at both of its call sites (RPC-9 and RPC-11) rather than shared. Both are proven at **every** call site by T7I-21, T7I-32, T7I-43, T7I-57 and T7I-60, not at one representative site. **This matters more under the two-stage workflow, not less.** There are **fifteen** emitting call sites across two actor roles, derived per RPC: RPC-1 **1**, RPC-2 **1**, RPC-3 **1**, RPC-4 **2**, RPC-5 **1**, RPC-6 **2** (one version-created plus one state-changed emitted only on the `needs_edit` origin), RPC-7 **0**, RPC-8 **1**, RPC-9 **1**, RPC-10 **1**, RPC-11 **2**, RPC-12 **2** — total **15**. Every one uses the shared construction.

**Event ordering within a transaction is ratified, not incidental.** Where an RPC emits two events, the order is **`report_version.created` (seq n) then `report.state_changed` (seq n+1)** — the version must exist before the transition that references it is recorded. `seq_no` is dense and the two events are hash-linked, so the order is frozen in tamper-evident evidence. §6.4 fixes Approve & Submit's two `report.state_changed` events in their own ratified order.

**Two registered actions in one RPC is A-029-conformant.** `report_version.created` is its own registered action, so version creation and state change are two *governed actions* in one transaction — A-029's "one event per governed action" is satisfied, not excepted.

| Event | Primary target | Related targets | state fields | Minimum payload |
|---|---|---|---|---|
| `report.created` (T0) | `report` / report id / label `Report` | `student`, `class_session` | all NULL (creation, not a transition) | report id, student id, session id, module id, observation id, `status:"incomplete"` |
| `report_version.created` (T3, T5, T6, T9, T12) | `report_version` / version id / label `Report version` | the owning `report`; the source version where `derived_from_version_id` is set; the trainer-approved source where set | all NULL | version id, `revision_number`, `content_hash`, `authored_by_role`, observation id + observation `lock_version` (derivation, where applicable), `derived_from_version_id` and `trainer_approved_source_version_id` where set |
| `report.state_changed` (T1, T2, T3, T4, T6, T7, T8, T10, T11×2, T12) | `report` / report id / label `Report` | the affected `report_version` where one exists; the `report_correction_request` on T10 | `state_domain='report'`, `state_from`/`state_to` = exact enum labels | version id and `content_hash` where a version exists; **on the trainer-approval event additionally the three checklist booleans and any resolved correction-request id**; **on T10 the correction-request id, `issue_scope` and affected `dimension_code`, and never the reason**; on the two T11 events the final version id, its `content_hash`, the trainer-approved source version id, and the checklist proof |

**Proofs:** every append is atomic with its mutation (single transaction); a failed or rolled-back operation appends nothing (gates fire before appends; rollback removes event + children + head update); fixture and test decoys remain rollback-only, so the committed chain stays empty until a real governed action occurs; management Approve & Submit emits exactly the two required consecutive state-change events.

### 10.1 Notification-trigger semantics (R-21b, A-039)

**Step 7I ratifies triggers and recipient rules only. It creates no notification table, enum, RPC, audit action, outbox row or delivery mechanism**, and it emits no notification of any kind.

| # | Trigger event | Recipient relationship (resolved live) | Minimum non-sensitive payload | Deduplication expectation |
|---|---|---|---|---|
| 1 | RPC-8 commits (`… → trainer_approved`) | every active `management` membership of the report's centre | report id, class-session id, student id, trainer-approved version id, occurrence timestamp — **identifiers and timestamps only** | at most one pending "final review required" notification per (report, trainer-approved version) |
| 2 | RPC-10 commits (`trainer_approved → needs_edit`) | the actively assigned trainer for the report's class session | report id, class-session id, student id, correction-request id, occurrence timestamp — **never the reason text** | at most one pending notification per correction request |
| 3 | RPC-11 commits (`approved → submitted`) | every parent holding an active `parent_student_links` row for the student | report id, class-session id, student id, submitted version id, occurrence timestamp | at most one per (report, submitted version); a later correction cycle that republishes produces a new notification for the new submitted version |

- **Timing is absolute, and it governs two distinct artefacts (disambiguated at Step 7I1D-R2).** The earlier form placed "created only after the transaction succeeds" immediately above "written inside the governed transaction", which reads as a contradiction. It is not — they describe different rows:

  | Artefact | Written | Survives only if | Failure behaviour |
  |---|---|---|---|
  | **Outbox row** — the durable intent | **INSIDE** the governed transaction, at the marked insertion point in §6.1 step 12, §6.3 step 9 and §6.4 step 12 | the governed transaction **commits** | cannot be lost once the transition committed |
  | **Notification record / delivery attempt** — the recipient-facing artefact | **AFTER** commit, by a separately driven worker reading committed outbox rows | — | a delivery failure **never** rolls back the committed transition; it is retried from the outbox |

  A rolled-back transition leaves **no outbox row**, so no notification record is ever created for one. **A post-commit hook with no in-transaction outbox row is prohibited**: it satisfies "only after success" and violates "never lost", producing a committed publication whose parent notification silently never happens.
- **Forward-compatibility consequence, recorded here rather than discovered later.** Because the outbox row is written **inside** the governed transaction, the notifications checkpoint must **replace** RPC-8, RPC-10 and RPC-11 (`CREATE OR REPLACE FUNCTION`) in its own migration to add that INSERT. Step 7I therefore authors those three so the insertion point is a **single, clearly commented location** in each. This is the same forward-compatibility discipline R-29 applied when it rejected audit-registry extension; its absence here was an asymmetry, not a decision.
- **Payload minimization:** identifiers and timestamps only. **No child name, account name, email address, phone number, report content, rating or correction reason.** A recipient's delivery address is resolved at delivery time from live authorization, never carried in the record.
- **No child PII enters an immutable audit event to support a notification** (R-30). The audit chain is not a notification carrier.
- **Later implementation owner:** the Phase 1 notifications checkpoint (`/server/modules/notifications`), which owns the outbox schema, the delivery worker, the channel choice and the recipient-preference model (U-31).

## 11. Failure and recovery semantics (R-22)

Every failure is deterministic, authored, and rolls back the entire transaction — current work is always preserved, and no failure appends an audit event. "UI refresh" = the client should re-read authoritative state via RPC-13/14/15 before retrying.

| Failure | Rolls back | Work preserved | Retry safe | UI refresh | Incident record |
|---|---|---|---|---|---|
| Unauthorized actor (wrong role, no session, no membership) | yes (nothing written) | yes | n/a — will fail again | yes | no |
| Inactive account or membership | yes | yes | after reactivation | yes | no |
| Unassigned trainer (assignment removed) | yes | yes | after reassignment | yes | no |
| No single active management membership (zero, or ambiguous) | yes | yes | after the membership is corrected | yes | **yes** if ambiguous — the partial unique index should make it impossible |
| Absent student (or missing attendance row) | yes | yes — existing rows retained (mid-cycle rule) | after attendance correction | yes | no |
| Withdrawn enrolment | yes | yes — existing rows retained | after re-enrolment | yes | no |
| Session start not yet reached | yes | yes | on/after the scheduled start in `Asia/Singapore` | yes | no |
| Missing required observation data (< 9 ratings) | yes | yes — observation work intact | after completing ratings | yes (jump-to-missing is UI's job) | no |
| Stale `lock_version` / stale status | yes | yes — the *winning* writer's work stands | yes, with refreshed expectations | **required** | no |
| Stale current-version id | yes | yes | yes, refreshed | **required** | no |
| Invalid transition (illegal from→to) | yes | yes | no — indicates a client bug | yes | no |
| Incomplete checklist at trainer approval | yes | yes | after completing checklist | yes | no |
| Evidence requirement unresolved | n/a in Phase 1 — the evidence condition **is** the checklist attestation (§3.4) | — | — | — | no |
| Content-hash mismatch (caller-supplied) | yes | yes | only after re-review of the current text | **required** | no |
| Stored content hash ≠ recomputed | yes | yes | no | **required** | **yes** — data-integrity anomaly; BUILD_NOTES incident |
| Wording-hash mismatch (management) | yes | yes | after re-reading the current candidate | **required** | no |
| **No trainer approval in the submitted version's lineage** | yes | yes | no — the report must be trainer-approved first | **required** | **yes** — reaching this gate means an earlier guard was bypassed |
| **Rating parity failure at submission** | yes | yes | no | **required** | **yes** — implies a wording edit mutated ratings; BUILD_NOTES + orchestrator report |
| Management field outside the allow-list | n/a — structurally unreachable; the RPC has no such parameter | — | — | — | **yes** if ever observed |
| Duplicate open correction request | yes | yes — the first request stands | no — resolve the open one first | yes | no |
| Duplicate request (unique-key violation) | yes | yes — the first request's outcome stands | yes — idempotent-by-gate | yes | no |
| Approval conflict (approval row already exists for that role) | yes | yes | no — version already approved by that role | **required** | no (expected under races) |
| Audit append failure (registry, actor validation, head anomaly) | yes — business mutation rolls back with it | yes | yes after cause addressed | yes | **yes** — never expected inside a governed RPC; BUILD_NOTES + orchestrator report |
| Publication failure (any step of RPC-11) | yes — no partial outcome; status is `trainer_approved` | yes | yes, refreshed | **required** | only if repeated/unexplained |

No error message reveals sensitive internal data (§8.6). The application does not auto-freeze on any failure; a chain-integrity finding follows the 7H baseline §6.3 incident posture.

## 14. Acceptance-test contract

Kinds: **S** static at review · **R** runtime · **(D)** transaction-local decoys, always rolled back · **(C)** coordinated concurrent sessions · **(V)** independent verification · **(M)** manual UI proof at a later checkpoint. Style: the 7H baseline §9 / `verify-local-fixtures.sql` precedent (exact FAIL labels, post-rollback residue proofs).

**Mandatory harness prerequisite — every runtime decoy that reaches a governed RPC must first establish a JWT identity context.** `audit_append_event` takes its authenticated branch **only** when `auth.uid()` IS NOT NULL, and on the system branch it rejects every `report.*` action outright; the Step 7G helpers likewise fail closed on a NULL `auth.uid()`. The committed `verify-local-fixtures.sql` is a plain owner-connection psql script with no JWT context anywhere, so a decoy copied from that harness would fail on **every** audit-emitting test for a reason unrelated to the property under test. Each such test therefore sets `SET LOCAL request.jwt.claims = '{"sub":"<fixture auth uid>","role":"authenticated"}'` (and `SET LOCAL ROLE authenticated` where EXECUTE posture is under test) before invoking any RPC. **Under the two-stage workflow the suite needs both the fixture trainer identity and the fixture management identity**, switching context between stages — the Step 7F fixture provides all three deterministic Auth identities, so no new fixture row is required.

**Database-isolation posture — ratified at Step 7I1D-R2 (U-7I-21), and a prerequisite for reading the kinds below.** The suite runs across **two** local databases:

| Database | Runs | Invariant |
|---|---|---|
| **Canonical** (the preserved fixture database) | every **S**, **R** and **R(D)** test, plus the preservation and repeatability proofs T7I-28, T7I-29, T7I-30 and T7I-31 | stays **pristine**: 3 Auth users, 25 domain rows, the fixture checksum byte-identical, the committed audit chain **empty**, the reconciled verifier passing twice |
| **Disposable** (created for the run, seeded by the same fixture loader, destroyed after) | the **four** **R(C)** coordinated two-session tests, and only these four: T7I-15, T7I-16, T7I-46 and T7I-61. **T7I-69 is `R(D)`, has no concurrent leg, and runs on the canonical database** (corrected at Step 7I1F-R3) | **deliberately dirty** — committed reports, versions, approvals and audit events are the *expected* outcome and no preservation assertion is ever made against it |

**Why this split is mandatory rather than tidy.** An `R(C)` test's whole property is *"exactly one writer commits; the loser fails CAS having written nothing"*. Under READ COMMITTED the loser can only observe the winner's row version **after the winner commits** — an uncommitted winner that rolls back lets the "loser" succeed, proving the opposite of the intended property. So every `R(C)` test **must commit** a governed mutation, and every such mutation appends an audit event in the same transaction. Those events are then **permanently uncleanable**: `audit_block_mutation()` raises unconditionally on UPDATE **or** DELETE with **no owner exemption and no session-variable bypass**, and Step 7H §6.4 forbids repair "ever". Run on the canonical database, the **four** `R(C)` tests would therefore leave T7I-28, T7I-30 and T7I-31 permanently red after the **first** execution, in a state no operation in the system can clean. The `(C)` kind previously carried no rollback discipline at all — `(D)` was defined as "always rolled back" and `(C)` merely as "coordinated concurrent sessions" — and that omission was the defect.

**Decoy identities use the three fixture identities only.** No test inserts into `auth.users` (`CLAUDE.md` §12 stop-and-ask), and none is needed: `accounts.auth_user_id` is FK'd to `auth.users`, so a fourth JWT-resolvable caller would require one. Every negative-identity case is instead constructed from the three ratified identities by **membership and assignment manipulation inside a rolled-back decoy** — an "unassigned trainer" by deactivating the fixture assignment; an "unrelated trainer" or "wrong-centre management" by adding a decoy centre and a decoy membership for the existing account, which R-28 resolves **per centre**; an "unlinked parent" by deactivating the fixture link. **Each test states its construction explicitly** rather than assuming one.
